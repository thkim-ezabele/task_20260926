# 보안 & 개인정보

> 인증/인가, 보안 정책, 직원 개인정보 보호 기준을 정의합니다. 🟡 표시는 해당 토픽(PRD)에서 정할 항목입니다.
>
> [위키 홈](../README.md)

## 기본 원칙

- **직원 연락처는 개인정보다.** 이름, 전화번호, 이메일, 주소는 업무에 필요한 최소한만 수집하고, 필요한 서비스만 가진다.
- **비밀 정보는 저장소에 두지 않는다.** 연결 문자열, 비밀번호, API 키, 토큰은 코드와 `appsettings.json`에 넣지 않는다.
- **최소 권한**: 사용자 권한, 서비스 DB 계정, 외부 연동 키 모두 필요한 범위만 준다.

## 인증 방식 (JWT / OAuth2)

- 🟡 인증은 Identity 서비스가 맡는다. 후보는 **JWT Bearer 토큰(자체 발급)** 또는 **OIDC / OAuth2**(외부 IdP 연동)이며, 인증 토픽에서 ADR로 정한다.
- 공통 원칙(방식과 관계없이):
  - 토큰은 짧은 만료 시간을 두고, 갱신 토큰을 쓰면 서버에서 폐기할 수 있게 한다.
  - 서명 키는 비밀 저장소에서 읽는다.
  - 토큰 · 비밀번호는 로그에 남기지 않는다.
  - 비밀번호를 직접 저장하게 되면 표준 해시(ASP.NET Core Identity `PasswordHasher` 등)만 쓴다.

## 인가 (역할 기반 권한)

- 권한은 **`[Flags]` enum 비트 마스킹**으로 표현하고 정수 컬럼 하나에 저장한다([ADR-0008](../03-architecture/adr/0008-integer-codes-and-bitmask.md)). 문자열 역할 / 권한 코드는 쓰지 않는다.
- 역할은 권한 조합의 별칭(코드상 `Admin = A | B | C`)으로 정의하고, 저장은 조합된 정수 값으로 한다.
- 인가는 API 엔드포인트에서 정책(`Authorization Policy`)으로 검사한다. 업무 규칙과 얽힌 권한(예: 자기 부서의 연락망만 수정)은 Handler / Aggregate에서 검사한다.
- 🟡 역할 · 권한 목록과 비트 배치는 인증 토픽에서 정하고 [데이터베이스 · 코드 정의](../04-development/database.md#코드-정의)에 기록한다.

## 서비스 간 인증

- 🟡 외부 요청은 API Gateway에서 인증하고, 내부 서비스는 Gateway가 전달한 토큰을 다시 검증한다(방식은 Gateway · 인증 토픽에서 결정).
- 통합 이벤트(메시지 브로커)는 브로커 계정 · 권한으로 서비스별 발행 / 구독 범위를 제한한다.

## 개인정보 보호 (연락처 암호화 / 마스킹 / 보관 기간)

| 항목 | 기준 |
|---|---|
| 수집 | 긴급 전파 · 응답 확인에 필요한 항목만 수집한다. 수집 항목은 PRD에서 정한다 |
| 로그 | **개인정보를 로그에 남기지 않는다.** ID로 대신한다([로깅 & 관측성 · 개인정보](../04-development/logging-observability.md#개인정보--보안)) |
| 마스킹 | 화면 · 응답 · 불가피한 로그에서 식별 정보를 보일 때 마스킹한다(예: `***-****-1234`). 마스킹 유틸리티는 BuildingBlocks에 둔다 |
| 전송 암호화 | 외부 통신은 HTTPS(TLS)만 허용한다. 운영 DB 연결은 TLS를 쓴다 |
| 저장 암호화 | 🟡 연락처 컬럼 단위 암호화 여부는 직원 · 연락처 토픽에서 정한다. 최소한 DB 볼륨 / 백업 암호화를 전제로 한다 |
| 보관 기간 | 🟡 긴급 상황 · 응답 기록의 보관 기간과 파기 방식은 해당 PRD에서 정한다 |
| 서비스 경계 | 개인정보는 필요한 서비스만 가진다. 다른 서비스에 복제할 때는 필요한 필드만 이벤트에 담는다 |
| 테스트 데이터 | 실제 직원 정보를 테스트 · 개발 데이터로 쓰지 않는다. 테스트 데이터 빌더로 만든 가짜 데이터를 쓴다 |

## 비밀 관리

| 환경 | 방식 |
|---|---|
| 로컬 개발 | .NET User Secrets(`dotnet user-secrets`) 또는 커밋하지 않는 `.env` |
| CI | GitHub Actions Secrets |
| 운영 | 🟡 환경 변수 / 비밀 저장소(Key Vault 등)는 배포 토픽에서 정한다 |

- `.gitignore`에 `.env`, `.env.*`, `appsettings.*.local.json`, `.claude/settings.local.json`이 포함되어 있다. 비밀이 커밋되면 즉시 키를 교체한다(이력에서 지우는 것만으로는 부족).
- 설정 구조는 [설정 & 시크릿 관리](../06-deployment/configuration.md)에서 정한다.

## DB 접근

- **서비스별 DB 계정**을 두고, 계정은 자기 서비스 Database에만 권한을 가진다([데이터베이스 · Database per Service](../04-development/database.md#database-per-service-원칙)).
- 읽기 연결(`ConnectionStrings:Read`)은 읽기 전용 트랜잭션으로 연다. 복제본을 도입하면 읽기 전용 계정으로 바꾼다([ADR-0009](../03-architecture/adr/0009-separate-read-write-db-context.md)).
- 애플리케이션 계정에는 DDL 권한을 주지 않고, 마이그레이션은 별도 계정 / 절차로 적용하는 것을 목표로 한다(🟡 배포 토픽에서 확정).
- 원시 SQL은 원칙적으로 쓰지 않는다(SQL 인젝션 위험 축소). 예외 승인 시에도 파라미터 바인딩만 쓴다.

## API 보안 (CORS / Rate Limiting)

- CORS: 기본은 허용하지 않는다. 프론트엔드 도입 시 허용 출처를 설정으로 명시한다(와일드카드 금지).
- Rate Limiting: ASP.NET Core Rate Limiting 미들웨어를 Gateway 또는 서비스에 적용한다. 🟡 한도는 Gateway 토픽에서 정한다.
- 입력 검증: 모든 Command / Query 입력은 FluentValidation으로 검증하고, 외부에서 들어온 코드값 · 비트 플래그는 정의 범위를 검사한다.
- 오류 응답은 `ProblemDetails`로 통일하고, 내부 예외 메시지 · 스택 추적을 응답에 넣지 않는다.

## 의존성 취약점 점검

- 패키지 버전은 `Directory.Packages.props`로 중앙 관리한다.
- 취약점 점검: `dotnet list package --vulnerable --include-transitive`. CI에 넣는 것을 목표로 한다.
- 🟡 Dependabot(또는 Renovate) 도입은 CI 구성 때 정한다.

## 감사 로그

- 🟡 긴급 상황 등록 · 전파, 권한 변경, 개인정보 조회 · 수정 같은 민감한 작업의 감사 기록(누가, 언제, 무엇을)은 해당 토픽에서 범위와 저장 방식을 정한다. 감사 기록에도 개인정보 원문은 남기지 않는다.

## 보안 체크리스트

- [ ] 비밀 정보가 코드 · 설정 파일 · 커밋에 없다
- [ ] 로그에 개인정보 · 토큰 · 비밀번호가 없다
- [ ] 외부 입력(코드값, 비트 플래그 포함)을 검증한다
- [ ] 엔드포인트에 인가 정책이 걸려 있다(익명 허용은 명시적으로)
- [ ] 오류 응답에 내부 정보가 노출되지 않는다
- [ ] 서비스 DB 계정이 자기 Database에만 접근한다
- [ ] 알려진 취약 패키지가 없다
