# ADR-0008: 코드값 정수화와 비트 마스킹

## 배경 (Context)

- 상태, 유형, 권한, 알림 채널 등 **코드값**이 여러 서비스에 걸쳐 쓰인다.
- 코드를 문자열(`'ACTIVE'`)로 저장하면 오타 · 대소문자 불일치가 생기고, 저장 공간과 인덱스 비용이 크며, 이름을 바꾸면 데이터 이전이 필요하다.
- 권한이나 알림 채널처럼 **여러 코드를 조합**해야 하는 값이 있다(예: SMS + 푸시).

## 검토한 대안 (Options)

1. **문자열 코드 (`varchar`)**: 사람이 읽기 쉽지만 위 문제가 있다.
2. **PostgreSQL `enum` 타입**: 타입 안전하지만 값 추가 · 삭제가 까다롭고 EF Core / 마이그레이션 관리가 번거롭다. 내부적으로도 이름 기반이다.
3. **정수 코드 + C# enum**: 저장 · 비교가 빠르고 이름 변경이 자유롭다. 의미는 코드 정의 문서로 관리해야 한다.
4. 조합 값: **조인 테이블** vs **비트 마스킹(정수 한 컬럼)**. 조인 테이블은 검색 인덱스가 쉽지만 조회 · 저장이 복잡하다. 비트 마스킹은 한 컬럼으로 저장 · 비교가 간단하지만 플래그 수에 상한이 있고 플래그 검색에 일반 인덱스를 쓰기 어렵다.

## 결정 (Decision)

**코드값은 문자열로 다루지 않는다(절대 금지). 정수 코드(대안 3)를 쓰고, 조합이 필요한 코드는 비트 마스킹을 쓴다.**

- 일반 코드: C# `enum : short` ↔ `smallint`. 모든 값 명시, `0` 예약, 배포된 값 재사용 금지, 체크 제약으로 허용 값 제한
- 조합 코드: C# `[Flags] enum : int / long` ↔ `integer` / `bigint`, 값은 `1 << n`, 비트 자리 재사용 금지, 체크 제약으로 정의 범위 제한
- **API 요청 / 응답, 통합 이벤트, 에러 코드도 정수**로 한다. `JsonStringEnumConverter`는 쓰지 않는다.
- C# enum이 코드 정의의 원본이고, 값과 의미는 위키의 코드 정의 표로 관리한다(DB 코드 테이블 없음).

## 결과 (Consequences)

- 긍정: 저장 · 비교 · 인덱스가 효율적이고, 코드 이름 변경이 데이터에 영향을 주지 않는다. 조합 코드를 컬럼 하나로 다룬다.
- 부정: DB와 API 응답만 보고는 코드 의미를 알 수 없다(코드 정의 표와 API 문서 필수). 비트 마스킹은 플래그 수 상한(31 / 63)이 있고, 플래그 조건 검색에 부분 인덱스 등 별도 고려가 필요하다.
- 후속: 서비스별 코드 정의 표를 [데이터베이스 · 코드 정의](../../04-development/database.md#코드-정의)에 유지하고, 에러 코드 범위를 [에러 코드](../../05-api/error-codes.md)에 정한다. 규칙 상세는 [코딩 컨벤션 · 코드값](../../04-development/coding-conventions.md#코드값-enum-규칙).
