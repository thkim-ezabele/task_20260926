# ADR-0006: TDD 개발 방법론 채택

## 배경 (Context)

- 긴급연락망은 장애나 오동작(전파 누락, 잘못된 집계)의 영향이 큰 시스템이라, 업무 규칙을 테스트로 보증해야 한다.
- 과제형 프로젝트로서 요구사항(FR)이 실제로 충족됐다는 **검증 가능한 증빙**이 필요하다.
- 1인 개발에 AI 에이전트가 코드를 작성하므로, 에이전트가 만든 코드가 요구사항과 규칙을 지켰는지 자동으로 확인할 수단이 필요하다.

## 검토한 대안 (Options)

1. **구현 후 테스트(Test-After)**: 장점: 초기 속도가 빠르다. 단점: 테스트가 뒤로 밀리거나 구현에 맞춰 작성되어, 실패 · 엣지 케이스가 빠지기 쉽다.
2. **통합 / E2E 테스트 중심**: 장점: 실제 흐름을 검증한다. 단점: 느리고 깨지기 쉬우며, 실패 원인을 좁히기 어렵다.
3. **TDD(Red → Green → Refactor)**: 장점: 요구사항을 테스트로 먼저 표현해 누락을 줄이고, 테스트 가능한 설계를 강제하며, 리팩터링 안전망이 된다. 단점: 초기 개발 속도가 느리고 테스트 작성 역량이 필요하다.

## 결정 (Decision)

기능 개발은 **TDD (Red → Green → Refactor)** 사이클을 따릅니다.

선정 사유:

- 테스트를 먼저 쓰면 **실패 · 엣지 케이스까지** 요구사항을 빠짐없이 표현하게 된다. 테스트할 동작마다 성공 / 실패 / 엣지 케이스를 필수로 한다([테스트 전략](../../04-development/testing-strategy.md)).
- 도메인 규칙을 프레임워크 없이 테스트하는 Clean Architecture(ADR-0003)와 잘 맞는다.
- 에이전트 워크플로우에서 **developer는 단위 테스트를 먼저 쓰고 구현**하고, **tester는 통합 · 인수 테스트로 FR 충족을 검증**한다. 테스트 통과가 단계 통과 조건이 되어 에이전트 결과를 자동으로 판정할 수 있다.
- 인수 테스트의 FR ID(`Trait`)가 요구사항 충족의 증빙이 된다.

## 결과 (Consequences)

- 도메인 / 애플리케이션 로직은 테스트를 먼저 작성합니다.
- PR은 테스트 통과를 필수 조건으로 합니다.
- 상세 규칙은 [TDD 가이드](../../04-development/tdd-guide.md)를 참고합니다.
- 부정: 기능당 테스트 코드가 구현보다 많아질 수 있다. 테스트 데이터 빌더와 공통 픽스처로 부담을 줄인다.
