# ADR-0002: 마이크로서비스 아키텍처(MSA) 채택

## 배경 (Context)

- 긴급연락망은 직원 / 조직 관리, 연락망 구성, 긴급 상황 전파, 채널별 알림 발송, 응답 집계, 인증처럼 **변경 이유와 부하 특성이 다른 영역**으로 나뉜다.
- 특히 알림 발송과 응답 수집은 긴급 상황에 부하가 몰리는 반면, 직원 / 조직 관리는 평소 변경이 적다. 부하가 큰 영역을 따로 확장할 수 있어야 한다.
- 외부 발송 채널(SMS, 푸시, 이메일) 장애가 전체 시스템 장애로 번지지 않아야 한다.
- 과제형 프로젝트로서 MSA 설계(경계 설정, 서비스 간 통신, 데이터 분리)를 증빙하는 것도 목표다.

## 검토한 대안 (Options)

1. **모놀리스(단일 애플리케이션)**: 장점: 개발 · 배포 · 트랜잭션이 가장 단순하다. 단점: 영역별 독립 확장과 장애 격리가 어렵고, 경계가 코드 규칙에만 의존해 쉽게 무너진다.
2. **모듈러 모놀리스**: 장점: 모듈 경계를 두면서도 배포는 하나로 단순하다. 단점: 알림 발송 같은 부하 영역을 따로 확장할 수 없고, 장애 격리가 제한적이다.
3. **마이크로서비스(MSA)**: 장점: 서비스별 독립 배포 · 확장 · 장애 격리, 경계가 물리적으로 강제된다. 단점: 서비스 간 통신, 분산 데이터 일관성, 관측성, 운영 복잡도가 커진다.

## 결정 (Decision)

시스템을 바운디드 컨텍스트 단위의 **마이크로서비스**로 분리합니다.

선정 사유:

- 알림 발송 · 응답 수집처럼 긴급 상황에 부하가 몰리는 영역을 **독립적으로 확장**할 수 있다.
- 외부 채널 장애를 서비스 단위로 **격리**할 수 있다.
- 바운디드 컨텍스트 경계가 서비스 · Database 경계로 강제되어, AI 에이전트가 작업해도 경계가 흐려지지 않는다.
- 운영 복잡도는 EDA(ADR-0004), 관측성(OpenTelemetry), 컨테이너 기반 로컬 환경으로 줄인다.

## 결과 (Consequences)

- 서비스별로 독립 배포와 독립 데이터 저장소(Database per Service)를 원칙으로 합니다.
- 서비스 목록은 [MSA 서비스 카탈로그](../service-catalog.md)에서 관리합니다.
- 서비스 간 통신, 분산 트랜잭션, 관측성에 대한 설계가 필요합니다.
- 긍정: 서비스별로 기술적 결정(스키마, 확장)을 독립적으로 할 수 있다.
- 부정: 1인 개발 기준으로 초기 구축 비용(서비스 뼈대, 인프라, 통합 테스트)이 크다. 서비스 수는 [서비스 카탈로그](../service-catalog.md) 확정 시 과도하게 늘리지 않는다.
